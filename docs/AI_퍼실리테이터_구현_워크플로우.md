# AI 퍼실리테이터 프로토타입 구현 워크플로우

**목표**: 다음 DBR 사이클(평가·성찰 단계)에 투입할 실사용 가능한 시스템
**기반 플랫폼**: 기존 오픈소스 블록 코딩 플랫폼 확장/커스터마이징
**개발 방식**: Claude Code / Antigravity 등 AI 코딩 에이전트를 활용한 바이브 코딩
**1차 구현 범위**: Table 1의 6개 트리거 중 1~2개로 핵심 개념 검증 후 확장

---

## 1. 왜 "이벤트 로거"부터 만드는가

Table 1의 6개 트리거는 결국 아래 4가지 원시 신호의 조합입니다.

1. AI 챗봇 메시지 (입력/응답, 타임스탬프, 키워드)
2. 코드 블록 변경 (추가·수정·삭제)
3. 실행(Run) 이벤트
4. 오류(에러 코드) 이벤트

트리거마다 감지 로직을 따로 짜면 6개를 유지보수하기 어렵습니다. 따라서 **트리거 로직보다 먼저, 이 4가지 신호를 하나의 통합 이벤트 스트림으로 뽑아내는 로거**를 만드는 것이 전체 작업의 기반입니다. 이후 트리거는 "이 스트림을 구독해서 조건이 맞으면 개입 이벤트 발생"이라는 동일한 패턴으로 계속 추가하면 됩니다.

## 2. 시스템 구성 요소

| 구성 요소 | 역할 |
|---|---|
| 블록 코딩 플랫폼 | 에디터 + AI 챗봇 사이드바 (바이브 코딩: 자연어 → 블록 생성/수정) |
| 이벤트 로거 | 4가지 신호를 세션ID·타임스탬프와 함께 기록 |
| 트리거 감지 엔진 | Table 1 조건을 이벤트 스트림에 적용, 조건 충족 시 "개입 이벤트" 발생 |
| 개입 전략 매니저 | 개입 이벤트 → 해당 인지적 도제 전략의 질문 문구 선택 → UI 노출 |
| 연구 데이터 저장소 | 트리거 발생 이력·학습자 반응을 비식별화하여 저장 (다음 사이클 평가 근거) |

## 3. MVP 범위 제안: 계획(Planning) 국면부터

Table 1의 트리거는 성격이 다릅니다.

- **단순 이벤트형** — 세션 시작, 첫 입력 감지 → 모델링·스캐폴딩
- **패턴/누적형** — 키워드 3회 반복, 오류코드 2회 반복, 30초 이내 재요청 → 코칭·명료화·성찰·탐색

**계획 국면의 두 트리거(모델링→스캐폴딩)** 는 둘 다 "세션 시작 후 첫 입력"이라는 동일한 단순 이벤트를 기준으로 합니다.

- 감지 로직이 가장 단순함 (boolean 상태 하나: 첫 입력 여부)
- 두 전략이 짝을 이루어 Table 1의 "2차원 구조"(국면×전략) 자체를 온전히 검증 가능
- 로거 → 감지 엔진 → 전략 매니저 → UI까지 전체 파이프라인을 가장 빠르게 끝까지 뚫어볼 수 있음

**➡ 추천: 계획 국면(모델링+스캐폴딩)으로 파이프라인 전체를 먼저 검증 → 점검 국면(코칭+명료화) → 수정 국면(성찰+탐색) 순으로 확장**

다만 "복잡한 패턴 감지가 실제로 가능한가"가 더 큰 리스크라고 판단되면, 수정 국면의 탐색(오류코드 반복) 트리거를 먼저 검증하는 것도 대안입니다. 아래 phase는 계획 국면 우선을 기준으로 작성했습니다.

## 4. 단계별 실행 계획

### Phase 0. 코드베이스 탐색 (반나절~1일)

**목표**: 베이스 플랫폼에서 4가지 원시 신호가 어디서 발생하는지 파악

Claude Code / Antigravity 프롬프트 예시:

```
이 저장소의 구조를 살펴보고, 다음 4가지 이벤트가 코드상 어디서 발생하는지 알려줘:
1) 사용자가 AI 챗봇에 메시지를 보내는 지점
2) 블록이 추가/수정/삭제되는 지점
3) 코드(블록) 실행이 시작되는 지점
4) 실행 중 오류가 발생하는 지점
각 지점의 파일 경로, 함수명, 이벤트명(있다면)을 표로 정리해줘.
아직 코드는 수정하지 말고 조사만 해줘.
```

**산출물**: 이벤트 소스 매핑 표 (파일:함수:이벤트명)

**이 단계에서 반드시 확인할 기술적 질문**:
- 오류가 분류 가능한 "코드" 형태로 나오는가, 자유 텍스트 스택트레이스만 나오는가? (→ 탐색 트리거 구현 난이도를 좌우함)
- AI 챗봇 메시지에 세션ID·타임스탬프가 이미 있는가, 새로 추가해야 하는가?

### Phase 1. 통합 이벤트 로거

**목표**: Phase 0에서 찾은 4개 지점에 공통 스키마로 로깅 훅 삽입

이벤트 스키마 예시:

```json
{
  "sessionId": "string",
  "timestamp": "ISO8601",
  "type": "ai_chat_input | ai_chat_response | block_change | run | error",
  "payload": {}
}
```

프롬프트 예시:

```
[Phase 0 결과 문서]를 참고해서, 다음 스키마로 이벤트를 발행하는 공통 로거 모듈을 만들어줘:
{sessionId, timestamp, type, payload}
4개 지점(채팅 입력/응답, 블록 변경, 실행, 오류) 각각에 이 로거를 호출하는 코드를 추가해줘.
기존 동작은 바꾸지 말고 로깅만 추가해줘.
```

### Phase 2. MVP 트리거 구현 — 계획 국면 (모델링 + 스캐폴딩)

- **감지 로직**: 세션 시작 이벤트 이후 첫 `ai_chat_input` 이벤트 발생 여부(boolean)
- **모델링**: 첫 입력 "이전" 상태에서 세션 시작 시 자동 노출 — 예: "어떤 기능이 필요하고 어떤 순서로 만들지?"
- **스캐폴딩**: 첫 입력 "감지 시점"에 노출 — 예: "어떤 부분을 스스로 해결할 수 있고, 어떤 부분에 AI 도움이 필요한지?"

**설계 확인이 필요한 지점**: 퍼실리테이터 메시지는 코드 생성 AI 챗봇과 **같은 말풍선**에 섞여 나오나요, 아니면 **구분되는 별도 패널/페르소나**로 나오나요? 아동이 "이건 AI가 아니라 안내 메시지구나"를 구분할 수 있어야, 논문에서 강조한 "최종 판단과 실행의 주도권은 학습자에게" 있다는 설계 논리와도 일관됩니다. → 별도 시각 스타일의 패널을 권장합니다.

### Phase 3. 파이프라인 검증

- 실제 학생 행동을 흉내낸 가짜 이벤트 시퀀스를 미리 만들어 재생(replay)하며, 트리거가 정확한 시점에 정확히 1번만 발생하는지 자동 테스트
- 이 시점에 "온전히 동작하는 최소 시스템"이 확보됩니다 (교수님께 중간 데모 시연 가능)

### Phase 4. 점검(Monitoring) 국면 확장 — 코칭 + 명료화

- **코칭**: 동일 키워드 포함 AI 질문 3회 이상 → 키워드 추출/매칭 방식 결정 필요 (완전 일치 vs 간단한 형태소·유사어 매칭. 초등학생 문장은 완전일치로는 놓치는 경우가 많을 가능성이 높음)
- **명료화**: AI가 새 코드 블록 제안 후 수정 없이 즉시 실행 감지 → "제안 시점"과 "실행 시점" 사이 diff 비교 로직 필요

### Phase 5. 수정(Modification) 국면 확장 — 성찰 + 탐색

- **성찰**: AI 제안 수락 후 30초 이내 다음 요청 → 타임스탬프 기반. 임계값(30초)은 잠정치이므로 설정값으로 분리해 추후 조정 가능하게 할 것
- **탐색**: 동일 오류 코드 2회 이상 반복 → Phase 0에서 확인한 "오류 분류 가능 여부"에 따라 난이도가 크게 달라짐. 자유 텍스트뿐이라면 최소한의 정규화·해싱이 필요

### Phase 6. 연구용 데이터 계층 + 아동 데이터 윤리 (실사용 사이클이므로 필수)

- 개인 식별 정보 없이 세션ID만으로 로그 저장 (비식별화)
- 수집 항목 최소화: 트리거 발생 시각·종류, 개입 노출 여부, 개입 후 행동 변화만 저장 (대화 원문 전체 저장 여부는 별도 검토)
- 보호자 동의/기관 승인 절차와 실제 로깅 스위치 연동 — 동의 없는 세션은 로깅 자체가 꺼지도록 설계
- 저장 위치(로컬 vs 클라우드)와 보존 기간 정책 문서화

### Phase 7. 교사-AI 협업 인터페이스 (선택, 확장 과제)

논문에서 언급된 "교사-AI 협업 조율" 관점을 실제 기능으로 — 교사가 트리거 발생 로그·임계값을 볼 수 있는 대시보드. 다음 이후 사이클 대상으로 미뤄도 무방합니다.

## Phase 8. 코드 도우미 실제 AI 연동

**목표**: Table 1의 6개 트리거 전부 완료 후, mock 응답으로 동작하던 "코드 도우미"에 실제 AI API 연동

**이유**: 트리거 로직 검증은 mock으로도 가능하므로, API 연동(요금/레이턴시/프롬프트 엔지니어링)은 분리해서 마지막에 처리

**확인할 것**:
- API 키 관리(.env, .gitignore)
- entryjs 블록 스펙에 맞는 응답 형식 설계
- 아동 대상 콘텐츠 필터링 필요 여부
- 실시간 응답 레이턴시

## 5. 바이브 코딩 세션 운영 팁

- 매 세션 시작 시 Table 1(트리거·전략·예시 문구)을 그대로 컨텍스트 문서(예: `FACILITATOR_SPEC.md`)로 만들어 AI 에이전트가 먼저 읽게 할 것 — 논문의 정의를 코드가 임의로 재해석하지 않도록
- Phase 단위로 커밋/체크포인트를 나누고, 매 phase 종료 시 "이 phase에서 구현한 것 / 구현하지 않은 것"을 요약받을 것
- Antigravity의 브라우저 서브에이전트는 실제 UI 클릭·스크린샷 검증에, Claude Code는 로거처럼 파일 수정이 많은 로직/백엔드 작업에 상대적으로 적합 — phase별로 도구를 나눠 쓰는 것도 방법

## 6. 다음에 확인이 필요한 것

1. 정확한 베이스 플랫폼(엔트리 / Scratch / Blockly 기반 등) — 정해지면 Phase 0 프롬프트를 해당 코드베이스에 맞게 더 구체화 가능
2. 오류 코드 감지가 실제로 가능한 실행 환경인지 (Phase 0에서 확인 후 판단)
3. 퍼실리테이터 메시지의 UI 노출 방식(같은 챗봇 vs 별도 패널) 결정
