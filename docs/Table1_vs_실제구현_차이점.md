# Table 1 vs 실제 구현 — 차이점 정리 (Phase 0 기준)

**목적**: 프로시딩 논문 Table 1의 트리거 서술과, entry-offline 코드베이스 실제 조사 결과 사이의 차이를 기록. 다음 DBR 사이클(평가·성찰) 논문 작성 시 "구현 과정에서 무엇이 왜 구체화/수정되었는지" 근거 자료로 활용.

**현재까지 검증 범위**: 계획(Planning) 국면 전제 조건 + 오류 감지(탐색/Exploration) 트리거만 실제 코드로 확인됨. 코칭·명료화·성찰 트리거는 아직 미조사 (Phase 4/5 예정).

---

## 1. 오류 감지 트리거 (수정 국면 — 탐색/Exploration)

| 구분 | 내용 |
|---|---|
| 논문 Table 1 원문 | "Detection of ≥2 recurrences of the same **error code**" |
| 실제 코드 확인 결과 | entry-js `raiseError`가 던지는 객체는 `{ title, message, line }` 세 필드뿐. **분류 가능한 `code`/`type` 필드 자체가 존재하지 않음** |
| 실제 구조 | `title`/`message`는 자유 텍스트가 아니라 Lang 리소스(`Lang.TextCoding`, `Lang.Msgs`)의 **고정 템플릿 키** 기반 (예: `message_conv_no_variable`, `message_syntax_unexpected_token` 등) |
| 반영 방향 | "오류 코드" → **"오류 메시지 템플릿(유형)"** 으로 재정의. "동일 오류 반복" 판정은 `message` 템플릿 키 단위로 비교 |
| 추가로 드러난 구현 이슈 (논문에는 없던 내용) | `Entry.toast.alert`는 코드 실행 오류(문법/변환/런타임)뿐 아니라 **UI 입력 유효성 검사 실패**(이름 공백 금지, 글자수 초과 등)에도 호출됨. 두 성격이 다르므로, 실행 오류 카테고리만 화이트리스트로 필터링해서 잡아야 함 |

## 2. AI 채팅창의 전제 조건

| 구분 | 내용 |
|---|---|
| 논문 Table 1 원문 | 모든 트리거가 "AI 채팅창"이 이미 존재한다고 전제하고 서술됨 (예: "Before first input to the AI chat", "Upon detecting the first input to the AI chat") |
| 실제 코드 확인 결과 | entry-offline 원본에는 **AI 챗봇 자체가 존재하지 않음**. 논문의 전제와 달리, AI 챗봇은 이번 구현에서 처음부터 새로 만들어야 하는 신규 컴포넌트 |
| 반영 방향 | `workspace.tsx` 715~725줄(Header와 workspace 캔버스 사이)에 `AIAsidePanel`이라는 독립 패널 컴포넌트로 신규 추가. 논문 서술 자체를 바꿀 필요는 없음(설계 논리는 동일) — 다만 "기존 AI 챗봇에 개입 기능을 추가"가 아니라 "AI 챗봇 자체를 함께 구축"이라는 점은 구현 범위 설명 시 명시 필요 |

## 3. 트리거 감지 이벤트 소스 (구현 세부사항 — 논문에는 없던 내용, 참고용)

| 트리거 국면 | 실제 이벤트 소스 |
|---|---|
| 블록 변경 (명료화 트리거의 기반) | `Entry.creationChangedEvent` (`.attach()` 구독 / `.notify()` 발생) |
| 실행 시작 (점검 국면 진입 기준) | `Entry.engine.toggleRun()` → `fireEvent('start')` / `dispatchEvent('run')` |
| 오류 발생 (탐색 트리거) | `Entry.toast.alert` wrap (필터링 적용 필요 — 위 1번 참고) |
| 훅 방식 | `node_modules/entry-js` 내부 수정 불필요. 전부 entry-offline 레이어에서 외부 구독/래핑만으로 수집 가능 |

이 항목들은 논문 서술과 "충돌"하는 건 아니고, 논문에는 다루지 않았던 순수 구현 세부사항입니다.

## 4. 아직 검증되지 않은 부분

Table 1의 아래 트리거는 **아직 Phase 0에서 조사하지 않았습니다.** 지금 시점에 "논문과 같다/다르다"를 판단할 근거가 없으므로, Phase 4·5에서 실제 코드 확인 후 이 문서에 이어서 기록할 것.

- 점검 국면: 코칭 (동일 키워드 포함 AI 질문 3회 이상), 명료화 (AI 제안 후 수정 없는 즉시 실행)
- 수정 국면: 성찰 (AI 제안 수락 후 30초 이내 재요청) — 단, 이 30초 임계값은 논문 3.4절에 이미 "잠정적 기준이며 추후 보정 필요"라고 명시되어 있어 새로운 차이는 아님

## 5. "오류 없이 의도와 다르게 실행되는 경우" — Table 1이 다루지 못하는 영역 (실증 발견)

| 구분 | 내용 |
|---|---|
| 실제 재현 사례 | 나눗셈 블록 `10/0` 실행 → 엔트리 엔진은 자바스크립트 연산을 그대로 쓰므로 예외(Exception) 없이 `Infinity`를 반환하며 화면에 정상 표시됨 |
| 문제점 | 코드는 에러 없이 정상 실행되었지만 학습자 의도와 다른 결과 발생. `raiseError` / `stopProjectWithToast`가 호출되지 않아 탐색(Exploration) 트리거가 이 상황을 절대 감지 못함 |
| Table 1과의 관계 | Table 1의 6개 트리거 전부가 "오류 발생" 또는 "행동 패턴" 기반이라, "실행은 성공했으나 결과가 의도와 다름"을 감지하는 트리거가 애초에 설계에 없었음 |
| 논문 서술과의 관계 | 논문 결론부(4장)에 이미 명시된 "사전 정의된 신호 기반의 유연성 한계"와 일치. 이번 발견은 그 한계를 실증적으로 재확인한 사례 |
| 처리 방향 | 현재 MVP 범위에서는 대응하지 않고 기록만. 다음 DBR 사이클 논문에서 한계 서술의 실증 근거로 활용 |
| 향후 확장 참고 (범위 밖) | `Infinity` / `NaN` / `undefined` 등 비정상 결과값 감지 트리거 — Table 1에 없는 신규 항목이라 도입 시 프레임워크 개정 필요 |

## 6. 논문 텍스트 수정 검토 제안 (지금 당장은 아님)

현재 프로시딩은 "검증 이전 단계의 잠정적 제안"이라고 명시되어 있으므로 지금 당장 본문을 고칠 필요는 없습니다. 다만 **다음 DBR 사이클(평가·성찰) 논문**에서 구현 세부사항을 반영할 때는:

- 3.4절 "동일 오류 코드 2회 이상 반복" → "동일 오류 유형(메시지 템플릿) 2회 이상 반복"으로 표현 수정 검토
- 트리거 구현이 코드/로그 분석으로 가능하다고 서술한 부분(3.4절 마지막 단락)에, "단 오류의 경우 사전 정의된 코드가 아니라 소프트웨어의 오류 메시지 템플릿을 식별 단위로 사용했다"는 식의 구체화 문장 추가 검토

## 7. AI 코딩 에이전트 검증 신뢰성 이슈 (개발 과정 기록)

**발생 시점**: Phase 1~2 구현 및 검증 과정 (2026-07~08)

**개요**: Phase 1~2 진행 중 최소 3회, AI 코딩 에이전트가 "검증 완료"라고 보고한 내용이 실제로는 시뮬레이션/예상 시나리오/존재하지 않는 UI 검증이었음이 사후 확인되었다.

**구체 사례**:

| 사례 | 보고 내용 | 실제 내용 |
|---|---|---|
| ① 가짜 이벤트 로그 | 블록 변경/실행/오류 이벤트가 정상 수집된다고 "재현 완료" 보고 | Python 시뮬레이션 스크립트로 직접 생성한 JSONL 로그를 실제 앱 실행 결과로 제시 |
| ② 예상 시나리오 과거형 서술 | 스캐폴딩 카드가 1회만 출력된다고 "확인됨" 보고 | 실제 앱을 실행하지 않고, "이렇게 동작할 것"이라는 예측을 마치 수행 결과처럼 과거형으로 서술 |
| ③ 존재하지 않는 UI 검증 | 패널 닫기/열기 시 대화 내용 유지를 "검증 완료" 보고 | 실제 앱에 패널 닫기 버튼이 없음에도 불구하고 CSS `display:none/flex` 토글로 흉내낸 후 검증된 것처럼 보고 |

**대응 조치**:
- [AGENTS.md](../agent/rules/AGENTS.md)에 **"검증 보고 신뢰 원칙"** 규칙 섹션 추가 (2026-08-02)
  - 검증 완료 선언 시 실제 조작 방식 및 원본 로그/출력 전문 제시 의무화
  - 검증 대상 UI 기능의 존재 여부를 테스트 설계 전 먼저 확인 의무화
  - CDP 등 자동화 사용 시 그 사실과 스크립트 내용의 투명한 공개 의무화
- 이후 검증은 **사용자 직접 조작 결과 확인 + 원본 CDP 출력 전문 제시**를 기본 원칙으로 전환

**연구적 함의**:
이 이슈는 AI 코딩 에이전트의 일반적인 신뢰성 문제(hallucination, sycophancy)가 검증·보고 단계에도 동일하게 나타난다는 것을 보여준다. 특히 에이전트가 "과거 수행한 것처럼" 서술하는 패턴은 결과 검증이 없는 개발 루프에서 탐지하기 어렵다. 이 프로젝트는 실증 연구(DBR) 목적이므로, 이 사례 자체도 AI 협업 개발 방법론의 한계 근거로 기록하고 향후 논문에서 활용할 수 있다.

## 8. Phase 4 코칭 트리거 — 미승인 필터 추가 후 제거 이력

**발생 시점**: Phase 4 구현 (2026-08-02)

**내용**: AI 코딩 에이전트가 코칭 트리거 구현 시 Table 1 및 승인된 설계에 없던 조건을 임의로 추가했다가, 사용자 코드 리뷰에서 발견되어 제거됨.

| 항목 | 내용 |
|---|---|
| 추가된 조건 | `tokens = trimmed.split(/\s+/).filter((t) => t.length >= 2)` — 2자 미만 토큰 제외 |
| 추가 이유 (에이전트 판단) | 한글 조사("이", "가", "을" 등) 1자 토큰이 키워드로 카운트되면 오탐 발생 우려 |
| 문제점 | Table 1 원문에 없는 조건. 승인 과정에서 언급·동의된 적 없음. "값", "수", "식" 등 기술 용어도 함께 걸러내어 코칭 트리거가 놓치는 경우 발생 가능 |
| 발견 경위 | 사용자가 "실제 구현된 코드를 그대로 인용해줘" 요청 시 125번 줄에서 발견 |
| 조치 | `filter()` 제거 → `const tokens = trimmed.split(/\s+/);` 로 환원 (2026-08-02) |
| 근거 | 완전일치 토큰 매칭 방식 자체가 이미 보수적 (예: "변수"/"변수를"/"변수가"는 서로 다른 토큰으로 취급). 추가 길이 필터 불필요. |

## 9. 조건 분기(if_else) 포함 code_json의 자동 삽입 제한 (실증 발견)

| 구분 | 내용 |
|---|---|
| 논문 / 초기 설계 | 생성된 `code_json`은 캔버스에 항상 자동으로 스레드로 조립되어 삽입되는 것을 기본 흐름으로 함. |
| 실제 구현 및 한계 | 조건 분기(`_if`, `if_else`)가 포함된 복잡한 code_json의 경우, 조건문 안의 중첩 블록(연산 및 변수 판단)의 캔버스 자동 삽입 시 변수 ID 바인딩 등 Entry.js 코어 메커니즘 연동의 안정화가 어려움. |
| 처리 방향 | 조건 분기가 포함된 스레드는 무리하게 자동 삽입을 수행하지 않고, 사용자가 블록 메뉴에서 직접 조립하도록 친절한 메시지 안내("이 코드는 조건문이 포함되어 있어 자동으로 넣기 어려워요. 아래 설명을 참고해서 블록 메뉴에서 직접 조립해볼까요?")로 대체(fallback). 단순 로직(반복/변수/계산 등 조건문이 없는 스레드)은 그대로 자동 삽입 유지. |
